# CBF + Cosine Similarity vs. WEKA Tree Classifier: Methodology

This document specifies how the Content-Based Filtering (CBF) course recommender is built
and how it is evaluated against a WEKA tree classifier. All numbers in the worked examples
(§13) are produced by `cbf_eval.py`; nothing is computed by hand.

> **Labelling convention.** Statements marked **[Theory]** come from Holland's RIASEC
> framework. Statements marked **[Engineering]** are design decisions of this project.
> Statements marked **[Assumption]** must be stated as such in the thesis.

---

## 1. System architecture

```
          ┌──────────────────────── Web application (PHP / PostgreSQL) ────────────────────────┐
          │ RIASEC questionnaire ──► assessments (6 scores) ──► live CBF recommendations (UI)  │
          └───────────────────────────────────────────┬────────────────────────────────────────┘
                                                      │ export (pseudonymised)
                                                      ▼
  ActualCourse (follow-up / enrolment records) ──► student_profiles.csv ◄── course_profiles.csv
                                                      │                         (32 courses)
                                     cbf_eval.py split (stratified, fixed seed)
                                   ┌──────────────────┴──────────────────┐
                              train.csv / .arff                     test.csv / .arff
                                   │                                     │
               ┌───────────────────┼──────────────────┐                  │
               ▼                                      ▼                  ▼
   Weight validation (§10)                  WEKA tree classifier   CBF evaluation
   cbf_eval.py weights                      trained on train.arff  cbf_eval.py cbf
   (choose encoding on TRAIN only)          tested on test.arff    → cbf_results.csv
               └──────────────────────────────────┬──────────────────┘
                                                  ▼
                                Fair comparison on the SAME test students (§9)
```

The CBF has no learnable parameters. The only design choice tuned from data is the rank
encoding, and it is chosen on the **training** split only, so the test split is never used
to make design decisions.

  unaffected.

  final codes and stores the originals in `programs.original_holland_code_enc` (§12).
- Course names differ slightly from the database. The database has "BS Multimedia Arts" and
  "BS Business Administration Major in …"; this file has "B Multimedia Arts" and "BSBA Major in …".
  Use one naming convention when exporting `ActualCourse`.

### `student_profiles.csv` (template: `student_profiles_TEMPLATE.csv`)

`StudentID, R, I, A, S, E, C, ActualCourse`

- `StudentID` is a pseudonymous code such as S001, never a name or school ID (Data Privacy Act of 2012, RA 10173).
- `R`–`C` are six continuous scores on a 0–1 scale (§4).
- `ActualCourse` must be one of the 32 course names exactly. It is used **only** as ground truth.

### `cbf_results.csv`, generated by `python3 cbf_eval.py cbf …`

`StudentID, Course, CosineSimilarity, Rank, Recommended, ActualCourse`

- There is one row for every student × every course (32 rows per student), so every similarity score is kept.
- `Rank` is a competition rank (1, 2, 2, 2, 2, 6 …). Courses with identical vectors share a rank.
- `Recommended` = 1 for the first K rows in rank order. Ties are broken by catalogue order for display only;
  metrics use the tie-aware rule in §9.
- `ActualCourse` is copied in for evaluation. It is never an input.

## 3. Course-vector conversion

**Vector order:** `[R, I, A, S, E, C]`.

**[Theory]** A Holland code lists a person's or environment's three most prominent types
**in order**. "IRC" means Investigative first, then Realistic, then Conventional.

**[Engineering] Rank-preserving encoding.** Each letter gets a weight by its position:

| Position in code | 1st | 2nd | 3rd | absent |
|---|---|---|---|---|
| Weight | 1.00 | 0.67 | 0.33 | 0.00 |

**Why keep the rank?** With binary encoding (1/1/1), IRC, RIC and ICR all become the same vector
`[1, 1, 0, 0, 0, 1]`. The CBF could then not tell BS Computer Science (IRC) from BS Civil
Engineering (RIC) or BS Computer Engineering (ICR). The validator's ICR revision of Computer
Engineering would also have **no effect at all**. This is verified in
`test_binary_encoding_loses_letter_order`. A rank-preserving encoding keeps the ordinal
information the validators put into each code, and makes the revisions matter. §13 shows
Computer Engineering moving from joint 7th to 1st for a sample student.

**Limitations. State these in the thesis:**

- **[Assumption]** 1.00 / 0.67 / 0.33 are equally spaced steps. That says the gap between the
  1st and 2nd letter equals the gap between the 2nd and 3rd. Holland's theory specifies an
  *order*, not *intensities* or intervals, so these values are a **design choice, not a
  validated psychological measurement**.
- 0.67 and 0.33 are rounded versions of 2/3 and 1/3. The web app currently uses 3/2/1, which is
  proportional to 1 : 2/3 : 1/3 and gives identical cosine values. Across 20,000 random
  students × 32 courses, the rounded and exact versions never differ by more than **0.003** in
  cosine.
- Every course vector has the same length, ‖C‖ = √(1² + 0.67² + 0.33²) = **1.2481**, so no
  course is favoured by vector size.
- Whether this encoding is *appropriate* is tested empirically in §10. It is not assumed.

## 4. Student-vector generation

1. **Source of scores.** The web app's questionnaire has 60 Likert items (1–5), 10 per RIASEC
   dimension. This gives six raw totals between 10 and 50 (`assessments.score_r … score_c`).
   - **[Assumption]** This item bank was written for the project (`db/seed_questions.php`), and
     its reliability and validity have not been established. Preferably use a published,
     validated RIASEC instrument with documented psychometrics, such as the O*NET Interest
     Profiler. Otherwise, at minimum report internal consistency (Cronbach's α per dimension)
     from your own sample.
2. **Scale to 0–1.** Choose one scale and report it.
   - `raw50` = score / 50. This only changes units: cosine values are **identical** to raw
     scores, because cosine ignores uniform scaling.
   - `minmax` = (score − 10) / 40. This removes the floor of 10 that every dimension has
     because each item is answered at least "1". It **does** change cosine values, because it
     shifts the vector. It can be included as a sensitivity analysis.
3. **Vector** = `[R, I, A, S, E, C]`, keeping all six continuous scores. The student is **not**
   reduced to a three-letter code, so differences such as I = 0.91 versus C = 0.78 still count.

**Where `ActualCourse` must come from.** This is the most important data decision.

- Grade 11 students have **not yet enrolled** in a college course, so the web app holds no
  actual course. Valid sources:
  - **(a) Prospective:** follow up the same students after enrolment, using enrolment records with consent.
  - **(b) Cross-sectional:** give the same questionnaire to current students in the 32 courses
    and use their enrolled course.
- Option (b) is faster, but interests measured *after* entering a course may already reflect
  that course. Report this as a threat (§11).
- The course a student *states* on the Career Worksheet is an **intended** course, not an
  actual one. If it is used, call the label `IntendedCourse` and say so.
- In that case, the web app's 0.30 stated-program bonus must **not** be part of the evaluated
  CBF, because it would put the label into the input (leakage). The evaluated CBF here is
  pure cosine similarity.

## 5. Cosine similarity

similarity(S, C) = (S · C) / (‖S‖ × ‖C‖)

- **Inputs.** S is the student vector (§4) and C is the course vector (§3). Both are
  non-negative, so the similarity lies between 0 and 1.
- **Zero vectors.** If either vector is all zeros, the similarity is defined as 0. There is no
  division by zero. This can only happen for a student whose answers are all at the floor,
  with `minmax` scaling.
- **No threshold.** A minimum similarity for a "valid" recommendation would have to be chosen
  from validation data, for example by checking how Hit@K varies with the cutoff. No value is
  assumed here.

## 6. CBF algorithm

```
INPUT : student s with scores R..C (ActualCourse is NOT passed in)
        course list (32 courses, FinalHollandCode), encoding w = (w1, w2, w3), N
1  S ← scale([R, I, A, S, E, C])                      # §4
2  for each course c:
3      Cv ← zeros(6); for position p, letter L in FinalHollandCode(c): Cv[index(L)] ← w[p]
4      sim[c] ← (S·Cv) / (‖S‖‖Cv‖), or 0 if ‖S‖ = 0 or ‖Cv‖ = 0
5  order courses by sim descending; equal scores share a competition rank
6  store sim[c] and rank for ALL 32 courses               # needed for evaluation
7  return the first N courses                             # Top-N recommendations
```

- **No exact match is needed.** The student's own top-3 letters (for example "AIS", which no
  course has) are never looked up. Every course is scored, and the closest ones are recommended.
  See `test_profile_with_no_exact_course_code_still_ranks_everything`.
- **Recommendations come from ranking, not availability.** Every course is scored, but a course
  is recommended only because of its similarity rank.

Implementation: `cbf_eval.py` → `holland_to_vector`, `student_vector`, `cosine`, `rank_courses`.
The web app's `lib/CBFEngine.php` implements the same computation (§12).

## 7. WEKA dataset

Generated by `cbf_eval.py split`:

```
@ATTRIBUTE R NUMERIC   …   @ATTRIBUTE C NUMERIC
@ATTRIBUTE ActualCourse {'BA Communication', … all 32 …}
```

- **Inputs:** exactly the CBF's six features, on the same scale.
- **`StudentID`** is excluded. An ID would let the tree memorise students.
- **`ActualCourse`** is the class only.
- **No derived features.** Nothing computed from the course choice, such as the course's
  Holland code, its college, or the CBF's own rank of it, is an input.
- **Same class list in both files.** All 32 classes are declared in train and test, so the
  headers are compatible.

## 9. Fair evaluation

The two methods produce different kinds of output:

- **CBF** produces a *ranked list* and uses no training labels. It is knowledge-driven: its
  "model" is the validated course codes.
- **J48** produces *one predicted class* and is fitted to the training labels.

Comparing CBF Hit@3 with J48 accuracy would therefore be unfair. Compare them on the **same
test students** at **matching output levels**:

| Level | CBF | J48 | Comparable? |
|---|---|---|---|
| **Top-1** (primary) | The top-ranked course is treated as a prediction. Report accuracy and macro/weighted precision, recall and F1 | Native prediction. Report the same metrics | ✅ Same task |
| **Top-K** (K = 3, 5) | Hit Rate@K, Precision@K, Recall@K, MRR | Rank the classes by J48's predicted probability, then compute the same metrics | ✅ Only if the J48 probability output is used |
| **Holland-code level** | `CodeHit@K`: the actual course's code is among the top-K courses' codes | — | CBF-specific diagnostic |

**Rules:**

- **Ties.** Where courses tie (identical codes), use *expected* values: the actual course is
  assumed equally likely to sit in any tied position. `tie_aware` implements this.
  - Example: a student in BS IT whose top score is shared by 4 IRC courses gets
    Hit@1 = 0.25 rather than 0 or 1.
  - J48 probability ties are treated the same way.
- **Single relevant course.** Each student has exactly one relevant course, so
  Recall@K = Hit Rate@K and Precision@K = Hit Rate@K / K. Report Hit Rate@K and MRR as the
  main ranking metrics, and say why Precision@K is low by design (it can never exceed 1/K).
- **Baselines.** Report baselines alongside both methods: random choice
  (Top-1 = 1/32 ≈ 0.031, Hit@K = K/32), and always predicting the most frequent course in
  the training set.
- **Significance:**
  - At Top-1, use McNemar's test on the paired correct/incorrect outcomes of the two methods.
  - For MRR or Hit@K, use the paired bootstrap confidence intervals reported by
    `cbf_eval.py weights`; the same function applies to any two methods.
- **Interpretation.** Do not declare a winner from accuracy alone. If J48 has higher Top-1 but
  CBF has comparable Hit@3, you can conclude that J48 learns this sample's label distribution,
  while CBF gives transparent, explainable shortlists that need no outcome data.

## 10. Weight-validation experiment

- **Encodings compared:**
  - binary: 1 / 1 / 1
  - steep: 1 / 0.50 / 0.25
  - flat: 1 / 0.75 / 0.50
  - **proposed: 1 / 0.67 / 0.33**
- **Data:** the **training** split only (`cbf_eval.py weights --students train.csv --k 3`).
- **Primary metric:** MRR. Secondary metrics: Hit Rate@3 and Top-1. Fix these before looking
  at any results.
- **Decision rule, fixed in advance:**
  - Keep the proposed encoding unless another encoding's 95% paired-bootstrap confidence
    interval for the MRR difference lies entirely above 0.
  - If no encoding is clearly better, keep the proposed one. It is the simplest equally spaced
    rank encoding and is consistent with the existing system.
- **Then:** evaluate the chosen encoding **once** on the test split.
- **How to report the result:**
  - If the results support it, write: "the empirical results support using the proposed
    encoding". Do not write that the weights are "scientifically validated".
  - If binary performs worse, that is direct evidence that preserving rank matters.

## 11. Threats to validity

1. **Ground-truth validity.** `ActualCourse` may reflect admission limits, cost, family
   influence or availability rather than interest fit. Intended course is only a proxy.
2. **Reverse causality** (cross-sectional sampling). Studying a course may shape the interests
   that are measured.
3. **Instrument validity.** The project questionnaire has not been psychometrically validated (§4).
4. **Expert-coding subjectivity.** Course codes come from the crosswalk and validator
   judgement. One reviewer's revisions may not generalise.
5. **Encoding assumption.** The equal-interval weights are a design choice (§3).
6. **Indistinguishable courses.** 22 codes for 32 courses puts a limit on CBF Top-1. For
   example, a student in any of the 6 RIC courses can reach at most 1/6 expected Top-1 from the
   RIC tie alone.
7. **Small, imbalanced sample across 32 classes.** J48 may overfit. Courses with one student
   cannot be tested (`split` reports them). Report per-class counts.
8. **Selection and timing.** The sample comes from one institution and one cohort. Grade 11
   interests may change before enrolment.
9. **Multiple comparisons.** Four encodings and several metrics. Pre-register the primary
   metric (§10).
10. **Leakage.** Controlled by design:
    - `ActualCourse` is never passed to the scorer (`test_actual_course_cannot_influence_ranking`).
    - `StudentID` is not a WEKA attribute.
    - The encoding is chosen on train only.
    - The split is fixed and stratified (`seed 42`).

## 13. Worked examples (student S001)

S = [0.72, 0.91, 0.40, 0.35, 0.60, 0.78]

‖S‖ = √(0.72² + 0.91² + 0.40² + 0.35² + 0.60² + 0.78²) = √2.5974 = **1.6116**

‖C‖ = **1.2481** for every code (§3).

| Code | Course vector C | S · C | Cosine |
|---|---|---|---|
| **IRC** (BS CS, IT, MedTech, ChemE) | [0.67, 1.00, 0, 0, 0, 0.33] | 0.72·0.67 + 0.91·1.00 + 0.78·0.33 = 1.6498 | 1.6498 / (1.6116 · 1.2481) = **0.8202** |
| **RIC** (Civil, Mech, EE, ECE, Aero, Marine Eng.) | [1.00, 0.67, 0, 0, 0, 0.33] | 0.72·1.00 + 0.91·0.67 + 0.78·0.33 = 1.5871 | **0.7890** |
| **AES** (BA Communication) | [0, 0, 1.00, 0.33, 0.67, 0] | 0.40·1.00 + 0.35·0.33 + 0.60·0.67 = 0.9175 | **0.4561** |
| ESI (Sustainability, original as stated) | [0, 0.33, 0, 0.67, 1.00, 0] | 1.1348 | 0.5641 |
| **EIS** (Sustainability, final) | [0, 0.67, 0, 0.33, 1.00, 0] | 1.3252 | **0.6588** |
| ESA (Tourism, original as stated) | [0, 0, 0.33, 0.67, 1.00, 0] | 0.9665 | 0.4805 |
| **SEA** (Tourism, final) | [0, 0, 0.33, 1.00, 0.67, 0] | 0.8840 | **0.4395** |
| RIC (Computer Engineering, original) | [1.00, 0.67, 0, 0, 0, 0.33] | 1.5871 | 0.7890 (joint rank 7) |
| **ICR** (Computer Engineering, final) | [0.33, 1.00, 0, 0, 0, 0.67] | 1.6702 | **0.8303 (rank 1)** |

**How to read these results:**

- **IRC beats RIC (0.8202 vs 0.7890)** because S001 is higher on I (0.91) than on R (0.72).
  Rank preservation captures exactly this. Under binary encoding the two would tie.
- **The revisions change recommendations.**
  - ESI → EIS raises Sustainability Management for this I-leaning student (0.564 → 0.659).
  - ESA → SEA lowers Tourism Management, because S001's S score (0.35) is weak (0.481 → 0.440).
  - RIC → ICR moves Computer Engineering from joint 7th to **1st**, because S001's C score
    (0.78) is strong and C is now the 2nd letter.
- **S001's own top-3 letters are I, C, R ("ICR")**, the order of their three highest scores.
  After the revision, this code exists (Computer Engineering), but the method doesn't depend
  on that. Without it, the IRC courses (0.8202) would simply lead.
- **S001's final Top-5:**
  1. Computer Engineering 0.8303
  2. CS, IT, MedTech and ChemE, tied at 0.8202 (shared rank 2)
