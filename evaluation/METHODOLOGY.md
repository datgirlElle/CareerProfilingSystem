# CBF + Cosine Similarity vs. WEKA Tree Classifier: Methodology

This document specifies how the Content-Based Filtering (CBF) course recommender is built
and how it is evaluated against a WEKA tree classifier. All numbers in the worked examples
(§13) are produced by `cbf_eval.py`; nothing is computed by hand.

> **Labelling convention.** Statements marked **[Theory]** come from Holland's RIASEC
> framework. Statements marked **[Engineering]** are design decisions of this project.
> Statements marked **[Assumption]** must be stated as such in the thesis.

---

## 1. System architecture

```
          ┌──────────────────────── Web application (PHP / PostgreSQL) ────────────────────────┐
          │ RIASEC questionnaire ──► assessments (6 scores) ──► live CBF recommendations (UI)  │
          └───────────────────────────────────────────┬────────────────────────────────────────┘
                                                      │ export (pseudonymised)
                                                      ▼
  ActualCourse (follow-up / enrolment records) ──► student_profiles.csv ◄── course_profiles.csv
                                                      │                         (32 courses)
                                     cbf_eval.py split (stratified, fixed seed)
                                   ┌──────────────────┴──────────────────┐
                              train.csv / .arff                     test.csv / .arff
                                   │                                     │
                                   ▼                                     ▼
                         WEKA tree classifier                      CBF evaluation
                         trained on train.arff                     cbf_eval.py cbf
                         tested on test.arff                       → cbf_results.csv
                                   └──────────────────┬──────────────────┘
                                                  ▼
                                Fair comparison on the SAME test students (§9)
```

The CBF has no learnable parameters and is not tuned on any data, so the test split is never
used to make design decisions.

### `student_profiles.csv` (template: `student_profiles_TEMPLATE.csv`)

`StudentID, R, I, A, S, E, C, course`. This is the adviser's layout. For example:

```
StudentID,R,I,A,S,E,C,course
student1,,x,,,x,x,bsit
```

- `StudentID` is a pseudonymous code such as S001, never a name or school ID (Data Privacy Act of 2012, RA 10173).
- `R`–`C`: **x** for each of the student's top 3 RIASEC types, **blank** otherwise (§4).
  Numeric scores are also accepted and are converted to top-3 x's the same way.
- `course` (or `ActualCourse`) is one of the 32 courses: a full name, or an unambiguous short
  name such as `bsit` or `bsa`. Unrecognised values are reported. It is used **only** as ground
  truth.
- **Exporting from the app:** `php db/export_riasec_csv.php > evaluation/student_profiles.csv`
  writes every student's latest result in this layout. The course column is left empty, to be
  filled in from enrolment records.

### `cbf_results.csv`, generated by `python3 cbf_eval.py cbf …`

`StudentID, Course, CosineSimilarity, Rank, Recommended, ActualCourse`

- There is one row for every student × every course (32 rows per student), so every similarity score is kept.
- `Rank` is a competition rank (1, 2, 2, 2, 2, 6 …). Courses with identical vectors share a rank.
- `Recommended` = 1 for the first K rows in rank order. Ties are broken by catalogue order for display only;
  metrics use the tie-aware rule in §9.
- `ActualCourse` is copied in for evaluation. It is never an input.

## 3. Course-vector conversion

**Vector order:** `[R, I, A, S, E, C]`.

**[Theory]** A Holland code lists a person's or environment's three most prominent types
**in order**. "IRC" means Investigative first, then Realistic, then Conventional.

**[Engineering] Encoding used by the system: binary.** Each RIASEC dimension is **1** if its
letter appears in the course's final Holland code (YES), and **0** if not (NO):

| Letter in the code? | Yes (1st, 2nd or 3rd letter) | No |
|---|---|---|
| Value | 1 | 0 |

Example: IRC → `[1, 1, 0, 0, 0, 1]`. This is set in `config/cbf.php`
(`holland_rank_weights = [1, 1, 1]`).

**What binary encoding means:**

- **Letter order is not used.** Codes with the same three letters get the same vector:
  IRC, RIC and ICR are all `[1, 1, 0, 0, 0, 1]`. Under binary, the CBF cannot distinguish
  BS Computer Science (IRC) from BS Civil Engineering (RIC) or BS Computer Engineering (ICR).
- **Validator revisions that only reorder letters have no effect on recommendations.** For
  example, Computer Engineering RIC → ICR, Sustainability ESI → EIS and Tourism ESA → SEA keep
  the same letters, so their vectors don't change. The revisions are still stored (§2).
- **The 32 courses collapse into only 11 distinct course vectors.** For example, 11
  courses share the letters I, R and C. Ties are therefore common (§9, §10, §11).
- Every course vector has the same length, ‖C‖ = √3 = **1.7321**, so no course is favoured by
  vector size.

**Why binary (YES / NO) and not weighted letter positions.** A Holland code states *which*
RIASEC types characterise a course. Giving the 1st, 2nd and 3rd letters different numeric
weights would require specific values (for example 1.00 / 0.67 / 0.33) that no published study
establishes for this purpose. The system therefore records only whether each type is present
(YES = 1) or absent (NO = 0). This is a design decision: it uses no unsupported numbers, at the
cost of ignoring letter order.

## 4. Student-vector generation

> **CBF revision (web app, current).** Following the latest adviser discussion, the web app's
> CBF (`lib/CBFEngine.php`) now uses the student's **actual RIASEC profile** as the student
> vector: each type's **mean item score** (raw total ÷ 10, so 1.0–5.0) in [R, I, A, S, E, C]
> order. Example: totals R45 I45 A45 S45 E35 C25 → S = [4.5, 4.5, 4.5, 4.5, 3.5, 2.5].
> Course vectors stay binary (§3), and there are no weights of any kind. This replaces the
> top-3 binary student vector described in item 3 below for the web app. The Python toolkit
> in this folder (`cbf_eval.py`) and the WEKA dataset format were **not** changed in this
> revision and still use the top-3 binary encoding; see §10a.

1. **Source of scores.** The web app's questionnaire has 60 Likert items (1–5), 10 per RIASEC
   dimension. This gives six raw totals between 10 and 50 (`assessments.score_r … score_c`).
   - **[Assumption]** This item bank was written for the project (`db/seed_questions.php`), and
     its reliability and validity have not been established. Preferably use a published,
     validated RIASEC instrument with documented psychometrics, such as the O*NET Interest
     Profiler. Otherwise, at minimum report internal consistency (Cronbach's α per dimension)
     from your own sample.
2. **Scale to 0–1.** Choose one scale and report it.
   - `raw50` = score / 50. This only changes units: cosine values are **identical** to raw
     scores, because cosine ignores uniform scaling.
   - `minmax` = (score − 10) / 40. This removes the floor of 10 that every dimension has
     because each item is answered at least "1". It **does** change cosine values, because it
     shifts the vector. It can be included as a sensitivity analysis.
3. **Vector (adviser's decision): top-3 binary.** The student's **three highest** RIASEC
   scores get **1 ("x")**, and the other three get **0**.
   - Example: scores C 41, I 39, E 39, A 37, R 36, S 32 → top 3 = C, I, E →
     `[0, 1, 0, 0, 1, 1]`.
   - **Ties** for 3rd place keep the R, I, A, S, E, C order. This is the same rule as the
     assessment's stored top types.
   - Set in `config/cbf.php` (`student_vector = 'top_binary'`, `student_top_n = 3`).
   - **Trade-off.** How much stronger one type is than another is no longer used. For example,
     I = 45 and I = 31 both count as "x" if I is in the top 3. The alternative
     (`student_vector = 'scores'`) keeps all six scaled scores.

**Where `ActualCourse` must come from.** This is the most important data decision.

- Grade 11 students have **not yet enrolled** in a college course, so the web app holds no
  actual course. Valid sources:
  - **(a) Prospective:** follow up the same students after enrolment, using enrolment records with consent.
  - **(b) Cross-sectional:** give the same questionnaire to current students in the 32 courses
    and use their enrolled course.
- Option (b) is faster, but interests measured *after* entering a course may already reflect
  that course. Report this as a threat (§11).
- The course a student *states* on the Career Worksheet is an **intended** course, not an
  actual one. If it is used, call the label `IntendedCourse` and say so.
- In that case, no stated-program bonus may be part of the evaluated CBF, because it would put
  the label into the input (leakage). The web app's former 0.30 bonus has been removed; its CBF
  is pure cosine similarity.

## 5. Cosine similarity

similarity(S, C) = (S · C) / (‖S‖ × ‖C‖)

- **Inputs.** S is the student vector (§4) and C is the course vector (§3). Both are
  non-negative, so the similarity lies between 0 and 1.
- **With top-3 binary students and binary courses,** both vectors have exactly three 1s, so:

  similarity = (number of letters the student and course share) ÷ 3

  The only possible values are **3/3 = 100%**, **2/3 ≈ 67%**, **1/3 ≈ 33%** and **0/3 = 0%**.
- **Zero vectors.** If either vector is all zeros, the similarity is defined as 0. There is no
  division by zero. This only happens for a student with no assessment.
- **No threshold.** A minimum similarity for a "valid" recommendation would have to be chosen
  from validation data, for example by checking how Hit@K varies with the cutoff. No value is
  assumed here.

## 6. CBF algorithm

```
INPUT : student s with scores R..C (ActualCourse is NOT passed in)
        course list (32 courses, FinalHollandCode), encoding w = (w1, w2, w3), N
1  S ← top3_binary([R, I, A, S, E, C])                # §4: 1 for the 3 highest, else 0
2  for each course c:
3      Cv ← zeros(6); for position p, letter L in FinalHollandCode(c): Cv[index(L)] ← w[p]
4      sim[c] ← (S·Cv) / (‖S‖‖Cv‖), or 0 if ‖S‖ = 0 or ‖Cv‖ = 0
5  order courses by sim descending; equal scores share a competition rank
6  store sim[c] and rank for ALL 32 courses               # needed for evaluation
7  return the first N courses                             # Top-N recommendations
```

- **No exact match is needed.** The student's own top-3 letters (for example "AIS", which no
  course has) are never looked up. Every course is scored, and the closest ones are recommended.
  See `test_profile_with_no_exact_course_code_still_ranks_everything`.
- **Recommendations come from ranking, not availability.** Every course is scored, but a course
  is recommended only because of its similarity rank.

Implementation: `cbf_eval.py` → `holland_to_vector`, `student_vector`, `cosine`, `rank_courses`.
The web app's `lib/CBFEngine.php` implements the same computation (§12).

## 7. WEKA dataset

Generated by `cbf_eval.py split`:

```
@ATTRIBUTE R NUMERIC   …   @ATTRIBUTE C NUMERIC
@ATTRIBUTE ActualCourse {'BA Communication', … all 32 …}
```

- **Inputs:** exactly the CBF's six features: 1 (x) / 0 (blank) for each RIASEC type.
- **`StudentID`** is excluded. An ID would let the tree memorise students.
- **`ActualCourse`** is the class only.
- **No derived features.** Nothing computed from the course choice, such as the course's
  Holland code, its college, or the CBF's own rank of it, is an input.
- **Same class list in both files.** All 32 classes are declared in train and test, so the
  headers are compatible.

## 9. Fair evaluation

The two methods produce different kinds of output:

- **CBF** produces a *ranked list* and uses no training labels. It is knowledge-driven: its
  "model" is the validated course codes.
- **J48** produces *one predicted class* and is fitted to the training labels.

Comparing CBF Hit@3 with J48 accuracy would therefore be unfair. Compare them on the **same
test students** at **matching output levels**:

| Level | CBF | J48 | Comparable? |
|---|---|---|---|
| **Top-1** (primary) | The top-ranked course is treated as a prediction. Report accuracy and macro/weighted precision, recall and F1 | Native prediction. Report the same metrics | ✅ Same task |
| **Top-K** (K = 3, 5) | Hit Rate@K, Precision@K, Recall@K, MRR | Rank the classes by J48's predicted probability, then compute the same metrics | ✅ Only if the J48 probability output is used |
| **Holland-code level** | `CodeHit@K`: the actual course's code is among the top-K courses' codes | — | CBF-specific diagnostic |

**Rules:**

- **Ties.** Where courses tie (identical codes), use *expected* values: the actual course is
  assumed equally likely to sit in any tied position. `tie_aware` implements this.
  - Example: a student in BS IT whose top score is shared by 4 IRC courses gets
    Hit@1 = 0.25 rather than 0 or 1.
  - J48 probability ties are treated the same way.
- **Single relevant course.** Each student has exactly one relevant course, so
  Recall@K = Hit Rate@K and Precision@K = Hit Rate@K / K. Report Hit Rate@K and MRR as the
  main ranking metrics, and say why Precision@K is low by design (it can never exceed 1/K).
- **Baselines.** Report baselines alongside both methods: random choice
  (Top-1 = 1/32 ≈ 0.031, Hit@K = K/32), and always predicting the most frequent course in
  the training set.
- **Significance:**
  - At Top-1, use McNemar's test on the paired correct/incorrect outcomes of the two methods.
  - For MRR or Hit@K, use a paired bootstrap confidence interval over students
    (`paired_bootstrap` in `cbf_eval.py`).
- **Interpretation.** Do not declare a winner from accuracy alone. If J48 has higher Top-1 but
  CBF has comparable Hit@3, you can conclude that J48 learns this sample's label distribution,
  while CBF gives transparent, explainable shortlists that need no outcome data.

## 10. Encoding decision, tie handling and counseling referral

- **Encoding:** binary (YES = 1 / NO = 0) for both students (top 3 RIASEC types) and courses
  (letters of the final Holland code). Weighted letter positions are **not used** (§3).
- **Ties between courses.** Courses with the same score keep the same match percentage. When
  more courses tie than fit in the Top-3, they are listed in course-list order. The evaluation
  counts tied courses as equally likely (§9).
- **Ties in the student's top 3.** When two RIASEC scores tie for 3rd place, the letter that
  comes first in R, I, A, S, E, C order receives the x. This is the same rule the assessment uses
  for the student's stored top types.
- **Counseling referral.** A result is referred to **face-to-face counseling** with a Guidance
  Counselor when it is either:
  - **flagged**: low confidence. The top score is below the threshold in Security
    Configuration (default 50%), and the result appears in Monitoring automatically.
  - **not aligned**: the student's Preferred Course (Career Electives Worksheet) is not among
    their Top Matches. It is shown in its own "Your Preferred Course" section, marked
    "Worth a second look", with a suggestion to talk to a Guidance Counselor.

  In counseling, the counselor can review and revise the recommendation. The system's Top
  Matches are not final in these cases, and **this is a limitation of the study** (§11).
- **Match / mismatch (team definition).** Each saved result is classified as `match` or
  `mismatch` (`RecommendationPipeline::combine`, stored in `recommendations.match_status`):
  - **Final rule (prediction model enabled):** a **mismatch** is when the prediction model and
    the CBF have **no course in common**. The student then sees the CBF matches ("Top Matches
    According to the Guidance") with a note recommending a Guidance Counselor.
  - **Interim rule (until then):** a **mismatch** is when the student's Preferred Course is
    **not among the CBF matches**.
  - Under both rules, a student with no CBF match at all is a mismatch.

  The switch is a single setting in `config/cbf.php` (`decision_tree.enabled`).

## 10a. Recommendation sources (web app, CBF revision)

Implemented in `lib/RecommendationPipeline.php`. Three recommendation sources are kept
separate; none is given a numeric weight, and the worksheet never enters the cosine formula.

| Source | Question | Method | Status |
|---|---|---|---|
| **1. CBF** | Which courses have RIASEC characteristics most similar to this student's RIASEC profile? | student vector (mean item scores) vs. every course's binary Holland-code vector, cosine similarity | active |
| **2. Worksheet** | Which course does the student's Career Electives Worksheet indicate? | the Preferred Course | active |
| **3. Prediction model** | What course does the model predict from patterns in the training dataset? | WEKA decision tree | **not available** (no real dataset yet); excluded |

- **CBF candidates:** every course tied at the highest cosine similarity. Because course vectors
  are binary, courses with the same three letters (e.g. IRC, RIC, ICR) always have the same
  similarity, so there are usually several candidates.
- **Best Match (current):** the courses common to the available sources, i.e. CBF candidates ∩
  the Preferred Course. **Alternative Courses:** the other CBF candidates.
- **No common course:** no Best Match; the CBF candidates are shown as alternatives and the
  student is encouraged to talk to a Guidance Counselor (status `mismatch`).
- **Not final:** the result is stored and shown as incomplete (`pendingSources = prediction`)
  until the prediction model exists; the three-way intersection is not executed.
- **Stored per result** (`recommendations`): every course's dot product, magnitudes and cosine
  (`scores`), the CBF candidates (`cbf_program_ids`) and the Best Match (`final_program_ids`).
- **Auditing:** the staff page `cbf-debug` (and `php db/cbf_debug.php <school_id>`) shows the
  student vector and, for every course, the course vector, dot product, magnitudes and cosine.
- **Cosine similarity is not accuracy.** It is shown as "Cosine Similarity: 0.xxx", never as a
  percentage. Accuracy belongs to the future prediction-model evaluation.

## 11. Threats to validity

1. **Ground-truth validity.** `ActualCourse` may reflect admission limits, cost, family
   influence or availability rather than interest fit. Intended course is only a proxy.
2. **Reverse causality** (cross-sectional sampling). Studying a course may shape the interests
   that are measured.
3. **Instrument validity.** The project questionnaire has not been psychometrically validated (§4).
4. **Expert-coding subjectivity.** Course codes come from the crosswalk and validator
   judgement. One reviewer's revisions may not generalise.
5. **Encoding decision.** Binary encoding ignores letter order (§3). IRC, RIC and ICR are
   treated as the same profile. This was chosen because weighted letter positions lack published
   support.
6. **Indistinguishable courses.** Under binary encoding, the 32 courses form only 11
   distinct vectors, which limits CBF Top-1. For example, the 11 courses with letters I, R and C
   always tie, so a student in any of them can reach at most 1/11 expected Top-1 from that tie
   alone.
6b. **Coarse similarity (top-3 binary students).** Similarity can only be 100%, 67%, 33% or
   0%, so many courses tie. For example, 5 courses tie at 100% for a C-I-E student. The ranking
   cannot use how much stronger one interest is than another. Report how often the Top-3 is
   decided by a tie (evaluation uses tie-aware expected metrics, §9).
7. **Small, imbalanced sample across 32 classes.** J48 may overfit. Courses with one student
   cannot be tested (`split` reports them). Report per-class counts.
8. **Selection and timing.** The sample comes from one institution and one cohort. Grade 11
   interests may change before enrolment.
9. **Multiple comparisons.** Several metrics are reported. Pre-register the primary metric
   (MRR for the CBF, Top-1 accuracy for the comparison) before seeing results.
10. **Leakage.** Controlled by design:
    - `ActualCourse` is never passed to the scorer (`test_actual_course_cannot_influence_ranking`).
    - `StudentID` is not a WEKA attribute.
    - The split is fixed and stratified (`seed 42`).
11. **Counseling referral.** Results that are flagged or not aligned are referred to
    face-to-face counseling, where the recommendation may be revised (§10). The system's own
    ranking is therefore not the final recommendation for these students, and the effect of
    counseling is outside the scope of the CBF evaluation.
